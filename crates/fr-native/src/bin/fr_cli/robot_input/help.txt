
Explicit foreground robot control (Linux native desktop):
fr robot session open NODE_ID --foreground --role control --accept-input
    --experimental-native --display HANDLE|only [native trust/display options] [--json]
fr robot input NODE_ID --connection-id ID --status [--json]
fr robot input NODE_ID --connection-id ID --lease HANDLE --request-id INTEGER
    --observation-id INTEGER --max-observation-age-ms 1..1000
    (--move X,Y | --click BUTTON,X,Y | --modified-click MODIFIER,...,BUTTON,X,Y
     | --drag BUTTON,X1,Y1,X2,Y2 | --modified-drag MODIFIER,...,BUTTON,X1,Y1,X2,Y2
     | --key USB_USAGE | --chord MODIFIER,...,KEY | --scroll X,Y,DX,DY
     | --modified-scroll MODIFIER,...,X,Y,DX,DY | --text-file PATH) [--json]

Find the public connection ID with fr robot session status NODE_ID --json.
Keep the foreground viewer focused. The explicit automation owner requests one
control lease and has no reconnect, clipboard, files or native input forwarding.
--status returns a bounded input observation with all view generations and a
local comparison lease handle. Ready observations also include input_support:
signed host-desktop bounds (x,y,width,height) and the original grant's supported
physical_keys, absolute_pointer, buttons, line_scroll and committed_text capabilities.
A missing/null input_support from an older owner means unknown support. Expiry
clears this metadata with the observation's authority handles; it grants nothing
on its own. Screenshot control_authority carries the same original support.
Source age includes measured clock uncertainty;
compositor submission is not proof of optical visibility or application success.
For an image tied to that input observation, use fr robot observe NODE_ID
--connection-id ID --screenshot /path/new-screen.png --json. Its control_authority
object supplies the original input handles for the pictured frame; do not replace
them with a subsequent --status read. Expired readiness clears those handles.

Use increasing nonzero request IDs. Each action pins the ORIGINAL observation;
a new status read cannot refresh an accepted command. Coordinates are signed
host desktop pixels. --move sends one absolute pointer state without a click,
key or wheel event. Its point must be inside the original granted display. It
waits for the original host's pointer receipt; a lost datagram or missing receipt
is an unknown effect, never an automatic retry or a refreshed observation.
Buttons are 1 primary, 2 secondary, 3 middle, 4 back, 5 forward.
--drag presses at X1,Y1, moves once with the button held, then releases at X2,Y2.
Both distinct endpoints must be inside the original granted display before any
press is sent. Each of its two reliable actions waits for its original receipt;
the original observation and deadline remain in force through the release.
This is a bounded single move, with no recorded path or persistent held button.
--modified-click and --modified-drag hold one to four distinct USB modifiers
(224..231) through the corresponding mouse gesture. For example,
--modified-click 224,1,640,360 requests physical left Ctrl + primary click.
Both keyboard and absolute-pointer/button control must be granted. The complete
modifier set and all points are checked before the first modifier press.
Modifiers press in ascending usage order; after the button release, modifiers
release in reverse order. Each of at most ten actions waits for its own receipt
under the same original observation and deadline.
--key taps a physical USB page-7 usage (decimal), not Unicode or a keyboard-layout
guess. Scroll deltas are integer lines on each axis, at most 120 in magnitude.
Large scrolls use up to eight reliable actions of at most 32 total lines each,
horizontal before vertical. Each waits for the preceding host receipt under the
same original observation and deadline; an interrupted prefix is never replayed.
--modified-scroll holds one to four distinct USB modifiers through all wheel
actions, then releases them in reverse order. For example,
--modified-scroll 224,640,360,0,-3 requests a left Ctrl + wheel gesture.
It requires keyboard, absolute-pointer and line-scroll control. The entire
gesture must fit ten actions, including modifier presses/releases: one modifier
allows every plain scroll; two allow at most 192 total lines, three 128, four 64.
The existing 120-line per-axis limit still applies. Invalid combinations refuse
before any modifier press; later failures use the same original-owner cleanup.
--chord holds one to four distinct USB modifiers (224..231) through one
non-modifier key tap; for example, 224,225,19 is physical left Ctrl+Shift+P.
Modifiers press in ascending usage order, then the key; releases run in reverse.
Each of at most ten transitions waits for its own original host receipt. The
original observation age and request deadline are checked throughout; neither
is refreshed between keys. Clicks and key taps use the same press/release gates.
--text-file reads one explicit regular file containing 1..4096 bytes of UTF-8.
It preserves the complete content, including whitespace, newlines and combining
characters. Empty, invalid UTF-8, oversized, symlink and special files refuse
without sending input. Text content is never a command-line argument or copied
to the clipboard. The original grant must report committed_text; the current
macOS host offers it only after its Quartz text preparation probe succeeds.
Older hosts and physical-key-only hosts keep their other input operations.
One text action checks the original host ticket before each complete Unicode
scalar. Partial receipts count the scalars already submitted; a supplementary
character's UTF-16 pair is indivisible. No suffix is retried after expiry or
uncertainty. The macOS executor refuses text while it holds remote keys/buttons.
Quartz submission does not prove an application accepted the text; some apps
ignore Unicode event strings. No native IME composition is added by this command.
Pointer replay, arbitrary batches and persistent held keys are unavailable.
Human keyboard/mouse events are not forwarded in this mode.

Results distinguish confirmed OS submission, partial effects, refusal, and an
unknown external effect. Partial/uncertain requests fence the original control
owner and trigger its existing held-state cleanup. Nothing is rolled back or
automatically retried. At most eight results are retained; older request IDs stay
consumed even after eviction. A duplicate must keep every original argument.
Focus loss, hiding/resizing, local close and authority expiry remain terminal.
